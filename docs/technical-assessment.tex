\section{Module 1 - System Design}

\subsection{Domain}

\begin{itemize}
  \item \textbf{INDIVIDUAL}: the tenant is policyholder and insured; the landlord is
  beneficiary; the policy has exactly one risk.
  \item \textbf{COLECTIVA}: a real-estate agency or co-property administration is the
  policyholder; tenants are insured and landlords are beneficiaries; the policy has one
  or more risks.
  \item Each policy has an effective period, monthly rent, and premium. Premium is
  \(\textit{monthly rent} \times \textit{term months}\).
  \item Renewal uses the original term duration, applies IPC to monthly rent and premium,
  and changes the status to \texttt{RENOVADA}.
  \item The platform creates, retrieves, and modifies both policy types. Collective
  policies allow risks to be added or cancelled. Creation and renewal produce email/SMS
  notification events.
\end{itemize}

\subsection{High-level architecture}

Policy and Risk are logical modules in one Spring Boot deployment. This keeps policy/risk
changes transactional while preserving clear boundaries. Stateless instances run behind
the API Gateway. Every policy or risk state change updates the database and stores a CORE
outbox event in one transaction. A worker then calls the agnostic WebLogic edit service,
so a temporary CORE outage does not reject an otherwise valid platform operation.

Rule-based automatic renewal is executed by a scheduled worker that selects eligible
policies and invokes the same renewal use case as the API. Creation and renewal events
are consumed by the Notification Service for email and SMS delivery.

\subsection{Three selected architectural patterns}

\begin{tabularx}{\textwidth}{@{}L{3.0cm}Y@{}}
\toprule
\rowcolor{SoftGreen}
\textbf{Pattern} & \textbf{Justification} \\
\midrule
\textbf{1. Modular monolith} &
Policy and Risk share transactional rules. One deployable avoids distributed
transactions and unnecessary operational complexity while module interfaces preserve
an extraction path. \\
\textbf{2. Hexagonal architecture} &
Domain rules depend on ports rather than HTTP, JPA, WebLogic, or notification providers.
The CORE and persistence adapters can therefore be replaced and tested independently. \\
\textbf{3. Event-driven integration with transactional outbox} &
Policy changes and delivery intent commit atomically. CORE and notification delivery can
retry asynchronously with stable event identifiers, protecting availability and
preventing lost updates. \\
\bottomrule
\end{tabularx}

\subsection{Main data model}

\textbf{Policy} stores identity, type, status, effective dates, original duration,
monthly rent, premium, policyholder, beneficiary, and optimistic version.
\textbf{Risk} stores identity, policy ID, property address, tenant, status, and version.
\textbf{CoreOutboxEvent} stores event ID, policy ID, event type, delivery status,
attempts, next attempt, and last error. Policy has one-to-many relationships with Risk
and CoreOutboxEvent. Monetary values use fixed decimal precision.

An individual policy is validated to have exactly one risk; a collective policy has one
or more. A cancelled policy cannot renew. Cancelling a policy cancels every risk in the
same transaction.

\subsection{Scalability, logs, fault tolerance, and API versioning}

\begin{tabularx}{\textwidth}{@{}L{3.0cm}Y@{}}
\toprule
\rowcolor{SoftGreen}
\textbf{Concern} & \textbf{Approach} \\
\midrule
Scalability &
Stateless API instances scale horizontally. Lists are paginated; indexes support policy
\texttt{(type,status)} and risk \texttt{(policy\_id)} queries. Renewal and outbox workers
process bounded batches. \\
Logs and observability &
Structured logs include correlation ID, route, duration, policy/event ID, and outcome.
Health, request latency/error metrics, CORE failures, retries, and outbox age are
monitored. Secrets and personal data are not logged. \\
Fault tolerance &
Database transactions, optimistic locking, timeouts, bounded retry with backoff,
idempotent event IDs, dead-letter handling, multi-instance deployment, and tested
database backups. \\
API versioning &
Expose major versions in the public path, for example \texttt{/api/v1}. Additive changes
remain compatible; breaking changes receive a new version with a published deprecation
period. The assessment routes remain unprefixed exactly as requested. \\
\bottomrule
\end{tabularx}

\section{Module 3 - Database Optimization}

The supplied query joins approximately 10 million orders with 500,000 customers and
filters customers from Mexico. I would first capture the actual plan with
\texttt{EXPLAIN ANALYZE} and measure row estimates, logical reads, join method, spills,
and elapsed time.

\begin{lstlisting}[language=SQL]
SELECT o.order_id, o.order_date, c.customer_name, o.total_amount
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
WHERE c.country = 'México';
\end{lstlisting}

\textbf{Strategy 1 - Index the filter and join keys.}

\begin{lstlisting}[language=SQL]
CREATE INDEX idx_customers_country_customer
  ON customers(country, customer_id);

CREATE INDEX idx_orders_customer
  ON orders(customer_id);
\end{lstlisting}

The first index finds the relevant customer IDs; the second avoids scanning all orders
during the join. If supported and justified by the measured workload, include projected
columns to reduce table lookups. The added storage and write cost must be monitored.

\textbf{Strategy 2 - Correct statistics and validate the execution plan.}

Refresh statistics and create a histogram for the potentially skewed
\texttt{customers.country} column. Verify that the optimizer starts with filtered
customers and chooses an indexed nested-loop join when the filter is selective, or a
hash join when it is not. Also correct implicit type/collation conversions and memory
shortages that cause hash or sort spills.

\textbf{Strategy 3 - Use a materialized reporting model for frequent reads.}

If this is a frequent report and slight staleness is acceptable, create a materialized
view containing the joined projection and index it by country. Refresh it incrementally
or from change-data capture. This moves repeated join cost away from the transactional
tables; the trade-off is refresh complexity and controlled data staleness.

\section{Module 4 - Git}

To bring only the urgent security fix from \texttt{main} into
\texttt{feature/new-login}, use \texttt{cherry-pick}:

\begin{lstlisting}[language=bash]
git fetch origin
git switch feature/new-login
git cherry-pick -x <security-fix-commit-sha>
\end{lstlisting}

\texttt{git cherry-pick} applies only the selected commit rather than all changes from
\texttt{main}. The \texttt{-x} option records the original commit SHA for traceability.
If conflicts occur, resolve them, run the tests, and use
\texttt{git cherry-pick --continue}; use \texttt{git cherry-pick --abort} if the change
cannot be safely resolved.

\section{Module 5 - Technical Leadership}

The team has eight developers, 40\% technical debt in key services, ten critical
incidents in the last month, a three-week feature deadline, inconsistent reviews and
standards, and two junior developers who need support.

\subsection{Five priorities for the first two weeks}

\begin{tabularx}{\textwidth}{@{}L{0.55cm}L{3.4cm}Y@{}}
\toprule
\rowcolor{SoftGreen}
\textbf{\#} & \textbf{Priority} & \textbf{Actions} \\
\midrule
1 & Stabilize critical services &
Review the ten incidents, fix the main recurring causes, assign service owners, and
establish on-call, actionable alerts, and runbooks. \\
2 & Agree on a safe three-week scope &
Define the smallest valuable vertical slice with explicit acceptance, security,
observability, and rollback criteria. Surface dependencies and risks to the business. \\
3 & Establish minimum standards &
Introduce a Definition of Done, protected main branch, CI, small pull requests, mandatory
review, and clear ownership. \\
4 & Prioritize technical debt by risk &
Rank debt by incident recurrence, security, and impact on the feature path. Schedule the
highest-risk items rather than attempting to remove an arbitrary percentage. \\
5 & Develop team capability &
Pair each junior with a senior, give them bounded production tasks and weekly learning
goals, and share incident and architecture knowledge across the team. \\
\bottomrule
\end{tabularx}

\subsection{Team organization}

Create two four-person pods: a \textbf{feature pod} responsible for the thin vertical
slice and a \textbf{reliability pod} responsible for recurring incidents, delivery
guardrails, and critical-path debt. Place one junior in each pod with a designated
mentor. Rotate an incident captain from the team so other developers retain focus.
Use one prioritized board, limited work in progress, daily risk coordination, small
changes, and shared primary/secondary ownership.

\subsection{Performance metrics}

\begin{itemize}
  \item \textbf{Reliability:} SLO attainment, critical incident count and recurrence,
  mean time to detect, and mean time to restore.
  \item \textbf{Delivery:} deployment frequency, lead time, cycle time, blocked time,
  and work-in-progress age.
  \item \textbf{Quality:} change failure/rollback rate, escaped defects, flaky tests,
  critical vulnerabilities, and review time.
  \item \textbf{Sustainability and outcome:} unplanned work, on-call load, knowledge
  coverage, feature adoption, and task success.
\end{itemize}

Metrics are evaluated as team and service trends, not as individual rankings.

\subsection{Mandatory engineering practices}

\begin{itemize}
  \item Protected main branch, CI checks, dependency/security scanning, and no direct
  production changes.
  \item At least one meaningful reviewer; code-owner or second review for critical and
  security changes.
  \item Automated tests appropriate to the risk, plus observability and rollback
  evidence in the Definition of Done.
  \item Short-lived branches, small pull requests, feature flags, and progressive
  delivery.
  \item Blameless incident reviews with owned corrective actions, service runbooks, and
  architecture decisions recorded for material changes.
\end{itemize}

\subsection{Managing business pressure}

Quality floors for security, data correctness, testing, observability, and rollback do
not move; scope does. I would present three explicit options: a safe thin slice in three
weeks, broader scope at a later date, or a controlled three-week beta for limited users.
The recommended option is the thin slice, demonstrated twice weekly and released behind
a feature flag with monitored rollout and stop conditions. If the requested date, scope,
and quality cannot all be maintained, document the trade-off, recommend an option, and
ask the accountable business owner to make the decision with the risk visible.
